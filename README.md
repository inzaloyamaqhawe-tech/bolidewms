# Bolide WMS — Warehouse & Production Management (Demo)

A fully self-contained **demo** build of a Warehouse & Production
Management System, rebranded for **Bolide Tanzania** — logo, colors
(the signature Bolide pink→orange gradient on near-black chrome), and
copy throughout. Every page and workflow is here — Dashboard, MO List,
Transfer Progress, Assigned MOs, Bulks (stock control + shortage
reporting), Reports, Reissue Requests, Production Users, Workstations —
running against generated fixture data instead of a real SQL Server
database.

This is a sibling build of the `wms-dsa` demo (same MOs, same fixture
data, same backend logic) with only branding changed. It's meant to be
pushed to its **own** GitHub repo and deployed as its own Render service
later.

This repo is **deploy-ready as a single Render Web Service**: one Flask
process serves both the API and the frontend from the same origin.

## Project layout

```
demo_server.py            Flask app - API + serves public/index.html
public/index.html         The frontend, rebranded (Bolide logo/colors,
                           backend URL read from window.location.origin
                           so it works unchanged locally or on Render)
public/assets/bolide-logo.jpg   Bolide Tanzania logo (from the Bolide
                           Tanzania Website project's /public/products/)
public/favicon.ico         Bolide favicon
generate_demo_data.py      Generates demo_data_seed.json from scratch
demo_data_seed.json        The generated fixture dataset (read-only seed)
demo_data.json             Created at runtime when you change anything
                           (picking, reissue requests, comments, stock
                           edits...). Not committed - delete it to reset.
requirements.txt, Procfile, render.yaml    Deploy config
```

## Run locally

```
pip install -r requirements.txt
python demo_server.py
```

Open **http://127.0.0.1:5057/** — that one URL serves everything.

## Deploy to Render

1. Push this folder to its own GitHub repo (not yet done — this build is
   waiting on a repo URL).
2. In Render: **New +** → **Web Service** → connect that repo.
   - Build command: `pip install -r requirements.txt`
   - Start command: `gunicorn demo_server:app --workers 2 --threads 4 --timeout 120`
   - Health check path: `/health`
   - (Or **New +** → **Blueprint** and point at the repo — `render.yaml`
     has all of the above already.)
3. Deploy. The frontend and API are served from the same Render URL, no
   extra configuration needed — `public/index.html` reads its own backend
   URL from `window.location.origin`.

## What's in the fixture data

Generated by `generate_demo_data.py` (same dataset as the `wms-dsa`
build, anchored to "today" = 11 Aug 2026):

- **62 Manufacturing Orders** across New / Started / Issued / Transferred /
  Completed stages, due dates from ~45 days overdue to ~4 months out
  (plus explicit MOs pinned to May and June 2026 so those months always
  have data too), across 10 customers and 6 assembly types.
- **A Bill of Materials per MO** — 3–7 lines from a 27-item fibre/RF
  cable-assembly catalogue, each with `Qty_Required` vs `Qty_Issued`.
- **Bulk warehouse stock** for every material (`total_stock`,
  `required_qty`, computed `shortage`) — ~40% deliberately understocked so
  the Bulks page's shortage report has something to show.
- **28 production floor workers** across the real 9-stage line (Cut → In
  Prep → Glue → Build → Scribe → Polishing → Scope → Measurement →
  Packaging).
- **Workstation completion history** driving Assigned MOs / Production
  Users.
- **12 reissue requests** in a mix of pending / accepted / rejected / done.
- A warehouse issue log (Reports) and a handful of MO comments.

## What's actually live, not just static

Because `demo_server.py` is a real (if small) backend, these flows work
end-to-end and persist across reloads:

- Issuing/picking materials on an MO — decrements bulk stock, bumps the
  MO's issued qty/status, logs a Reports entry.
- Requesting a reissue (DSA Prod) and approving/rejecting/completing it
  (Warehouse Admin).
- Adding MO comments, editing bulk stock levels, assigning MOs/workers to
  workstations.

## What changed from the `wms-dsa` build

Only presentation, nothing structural or data-related:

- Logo + favicon: Bolide Tanzania wordmark (`/assets/bolide-logo.jpg`),
  sourced from the Bolide Tanzania Website project.
- Colors: sidebar/chrome moved to near-black (`--brand-ink`), primary
  buttons/badges/active-nav-state use the Bolide pink→orange gradient
  (`--brand-gradient`) instead of navy blue. Status badge colors (New/
  Started/Issued/Transferred/Completed) were left alone on purpose — they
  encode meaning, not brand.
- Every "DSA Warehouse" / "Dartcom" text reference (page title, sidebar,
  print/report headers, bulk-issue and reissue documents) renamed to
  Bolide Tanzania.
- The MO/material/customer fixture data, the 4 logins, and all backend
  logic are byte-for-byte identical to `wms-dsa`.

## Resetting the demo

Delete `demo_data.json` and restart — it reloads from the untouched
`demo_data_seed.json`. To get an entirely fresh random dataset, re-run
`python generate_demo_data.py` first.

## What this is not

This is a demo/fixture build for showing the system off. It is not
connected to any real Bolide Tanzania system or data, and no real backend
(`vvd.py`) or real production frontend is part of this repo or touched by
anything here.
